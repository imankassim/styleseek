# Risk Register

Source: `STYLESEE1.docx` §16. Reviewed at each stage decision gate (architecture §17).

| Risk / assumption | Impact | Mitigation or evidence | Status |
|---|---|---|---|
| Too little genuine interaction data | Personalised and two-tower models may appear convincing without being valid. | Use human judgments and session features first; label synthetic behaviour; retain advanced models as experiments. | **Confirmed directly at Stage 13**: three learned-ranking model families (EXP40/41/43) all substantially underperformed the hand-tuned fusion baseline on 178 training rows — retained as documented, rejected experiments per the prescribed mitigation, not shipped. **Stage 14 deliberately sidesteps this**: no training or pooled/aggregate data at all — reads only the current session's own real clicks at request time. |
| Poor catalogue metadata | Semantic and lexical retrieval both degrade. | Quality gates, controlled vocabulary, provenance and error analysis. | Open |
| Popularity bias | Already popular products receive more exposure and clicks. | Separate relevance from popularity, cap soft boosts, monitor catalogue exposure. | Open |
| Position-biased clicks | Top-ranked products receive more clicks regardless of inherent relevance. | Do not equate raw clicks with relevance; use judgments and analyse exposure. | Open |
| Over-personalisation | History overrides the current query. | Apply constraints first and bound personalisation influence. | **Addressed at Stage 14**: the colour boost only runs when `parsed.colour is None` (an explicit colour in the query is a hard filter from Stage 9 and is never reached by personalisation code at all), only reorders the existing top-10 window, and needs 2+ same-colour clicks in the session before it does anything. Confirmed live — see `docs/progress.md` Stage 14 row. |
| Vector-only overreach | Exact brands, SKUs and hard terms may be missed. | Retain lexical retrieval and validate hybrid fusion. | Open |
| LLM parser unpredictability | Invalid filters or fabricated attributes. | Strict schema, allowed values, deterministic fallback and isolated evaluation. | Open |
| Index staleness | Outdated stock or deleted products remain searchable. | Synchronisation tests, freshness metric and source-of-truth checks. | Open |
| Latency growth | Each added model increases response time. | Retrieve in parallel where appropriate, precompute product embeddings, report p95, simplify if needed. | Open |
| Unlicensed content | Legal and ethical exposure. | Use permitted, owned or clearly synthetic data and media. | Open — see [`docs/data_sheets/catalogue_data_sheet.md`](data_sheets/catalogue_data_sheet.md) |
| Scope expansion | Website features obscure the search research. | Exclude payments and non-essential commerce workflows. | Open |
| Complex local setup | OpenSearch and containers may exceed local constraints. | Begin with simple local alternatives and move heavier services to an approved managed environment only when needed. | Open |

## Project-specific risks (added during delivery)

| Risk / assumption | Impact | Mitigation or evidence | Status |
|---|---|---|---|
| Kaggle dataset is too large for a manual browser download | Stage 4 (catalogue) blocked until dataset is available locally. | Used `kagglehub.dataset_download(...)` with a one-off Kaggle API token auth (`~/.kaggle/access_token`). | Resolved |
| This machine's C: drive had ~0 bytes free, then only ~12.4GB after cleanup — not enough for the full 23.1GB dataset (and risky even at 25GB given archive+extraction can transiently need ~2x) | Stage 4 blocked / risked a long failed download | Switched to `paramaggarwal/fashion-product-images-small` (~572MB, same 44,446-row catalogue/metadata, lower-res images only) — see `docs/data_sheets/catalogue_data_sheet.md`. | Resolved |
| No PostgreSQL or Docker installed locally | Stage 4 blocked — nowhere to run the source-of-truth database | Used a managed free-tier Postgres (Neon) instead of local install, per the deployment architecture's "managed relational database" cloud-oriented role (§10) — connection string kept in git-ignored `database/.env`. | Resolved |
| Naive per-row inserts over a remote (Neon) connection were far too slow for 44k+ rows (~0.35s/row, projected ~4+ hours) | Ingestion impractical at full scale | Switched to psycopg3 pipeline mode (`conn.pipeline()`), which batches statement dispatch instead of round-tripping per statement — full ingest (44,446 products + 216,108 variants) completed in ~69s. | Resolved |
| Kaggle API token was pasted in plaintext in chat rather than saved to a file out-of-band | Token exposed beyond the intended local-file-only handling | Stored only in the git-ignored `~/.kaggle/access_token` file, not persisted anywhere else (not in memory, not in repo); user was advised they can revoke/regenerate it from Kaggle settings if they want to be extra cautious. | Accepted (no further action planned) |
| uvicorn forces `WindowsProactorEventLoopPolicy` on Windows at `.run()` regardless of any asyncio policy set beforehand, which is incompatible with psycopg's async connection mode (needs a selector-based loop) | Backend couldn't connect to the database at all on this machine (local Windows dev) | Switched `backend/app/db.py` from an async to a sync `psycopg_pool.ConnectionPool`; FastAPI runs sync (`def`) route handlers in a thread pool automatically, so this doesn't block the event loop. Revisit if/when Stage 15 moves serving to Linux containers, where this wouldn't have been an issue. | Resolved |
| No Docker/local install for OpenSearch (Stage 8, BM25) | Stage 8 blocked | Used a managed free-tier OpenSearch (Bonsai) instead of local install, same pattern as Neon for Postgres — connection string kept in git-ignored `database/.env`. | Resolved |
| Small, hand-picked relevance judgment set caused genuinely good but ungraded results to score as irrelevant by default ("pooling bias") — hit 3 times during Stage 8 (EXP10, EXP13, EXP14), each time making a real experiment look worse than it was | Early experiment comparisons (e.g. "EXP14 synonyms are worse than EXP12") were backwards | Pooled candidates from multiple experiments' actual top results before trusting any comparison — judgment set grew from 18 to 230 graded products across two pooling passes. See `evaluation/relevance_rubric.md` rule 5. | Resolved |
| Two same-named local Python modules (`mapping.py` in both `search/` and `experiments/EXP14_synonym_expansion/`) collided via Python's by-name module cache, regardless of `sys.path` order — `search/index.py`'s own internal import won, so EXP14 silently rebuilt the *production* OpenSearch index with the wrong (non-synonym) settings on its first run | A full experiment run produced misleadingly plausible results from the wrong index; briefly left the production index rebuilt with correct data but no synonym support | Renamed the colliding module to `synonym_mapping.py`; verified via `client.cat.indices()` that only the intended index existed and was rebuilt correctly afterward. No data was lost. | Resolved |
| Hard-filtering on extracted `category`/`occasion` looked like an obvious win but measurably regressed overall ndcg@10 (0.766 → 0.660) — catalogue category/occasion tags don't always match how shoppers phrase things (every real "blazer" is tagged Formal/Casual, never "Smart Casual"; wedding-appropriate sarees are tagged saree, not dress) | Would have shipped a "safety" feature that silently excluded genuinely relevant results | Measured before shipping (Stage 9) rather than assuming filters are always safe just because they're deterministic; only colour/gender/price kept as hard filters, category/occasion remain free-text signals only. | Resolved |
| Local Stage 10 embedding job (44,446 products × 3 representations) built an index with `nmslib` k-NN engine, deprecated in OpenSearch 3.0+ — index creation failed outright on the first attempt | ~20 minutes of embedding work wasted before the failure surfaced (the error only appears at index-create time, not embedding time) | Switched to the `lucene` engine (built into OpenSearch core, no extra plugin) and re-ran; confirmed no data was lost since the embedding computation itself hadn't started yet. | Resolved |
| A quick benchmark of embedding throughput (1000 short strings, isolated script) suggested the full 44,446 × 3 embedding job would take ~70 minutes; a mid-run progress check briefly suggested it might be ~13 hours based on a misread of an unrelated stale process's runtime | Nearly caused an incorrect "this will take all day" conclusion to be reported to the user | Re-measured directly against the actual running job's own document count over a fixed wall-clock interval rather than trusting a proxy measurement; actual real-world rate was close to the original benchmark (~80 minutes total). Lesson: always verify a suspicious timing estimate against the thing itself, not an adjacent signal. | Resolved |
| Naive RRF (EXP32) and equal-weight score fusion (EXP33) both looked like reasonable ways to combine BM25 + vector search, but both measurably regressed ndcg@10 versus BM25 alone (0.755 → 0.549 and 0.673) despite improving recall — a much weaker ranker (vector, ndcg 0.293) drags down a much stronger one when trusted equally | Would have shipped a "smarter" hybrid retrieval that was actually worse at ranking than the simpler system it replaced | Measured three fusion strategies before choosing one; explicit 90/10 lexical/semantic weighting (EXP34) was the only config that improved both ndcg@10 and recall@50 simultaneously. Promoted only that one. | Resolved |
| Client-side test script measured `/search` latency at 2.4–3.3 seconds for hybrid retrieval — alarmingly high versus the ~350ms measured in isolated benchmarks | Nearly concluded the hybrid integration had a severe performance regression | Root cause was the test script's own use of `"localhost"` (Python `requests` on Windows tries IPv6 `::1` first, times out, falls back to IPv4) — switching the test to `127.0.0.1` showed real latency was ~650ms. Not a backend bug at all. Lesson: verify a suspicious client-side measurement isn't an artifact of the client before concluding the server is slow. | Resolved |
| Architecture §16 recommends retrieving lexical and semantic candidates in parallel to control latency — implemented via a `ThreadPoolExecutor`, but measured *slower* (~1050ms) than sequential (~650ms) in practice, likely nested-thread-pool overhead on top of FastAPI's own per-request worker thread | Would have shipped a "latency optimisation" that was actually a regression | Measured both configurations before choosing; kept sequential retrieval since it was faster in practice on this platform, rather than assuming the architecturally-recommended approach must be better without checking. | Resolved |
| Manually verifying Stage 14's personalisation boost, two identical repeated `/search?q=dress` calls (same session, same query, no state change between them other than click events) returned candidates in a slightly different relative order among items with likely-tied BM25 scores | Could look like a personalisation bug (results changing when they "shouldn't") when it's actually pre-existing retrieval-layer behaviour | Confirmed the effect is independent of the personalisation code (the explicit-colour hard filter path, which never touches ranking order, was unaffected; only the colour-free broad query showed it). Not chased further — OpenSearch/Lucene doesn't guarantee stable ordering across score ties without an explicit tiebreaker sort, and no requirement calls for exact repeat-query stability. Integration tests for personalisation (`tests/integration/test_api_contract.py`) use structural invariants (all-matches-before-non-matches) rather than exact-order or exact-list equality, so they aren't sensitive to this. | Accepted (no further action planned) |
